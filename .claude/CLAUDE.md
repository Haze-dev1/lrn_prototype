## Architecture

```
Browser ──▶ proxy (Caddy :8080)
              ├── /api/*  ──▶  api (FastAPI :8000)
              └── /*      ──▶  web (Next.js :3000)

api, scheduler ──▶ postgres   durable source of truth
               └─▶ redis      locks, rate limits, idempotency, cache
```

Six services, identical in development and production. `docker-compose.yml` is production-shaped;
`docker-compose.override.yml` is auto-loaded in development and only ever *adds* source mounts,
hot reload and loopback datastore ports.

### Backend layering

```
route → controller → service and/or CRUD → model/database or external provider
```

- **Routes** (`core/apis/routes/`) — HTTP only: method, path, auth decoding, request parsing,
  response schema, route-level error handling. No queries, no provider calls, no workflows.
- **Controllers** (`core/controllers/`) — domain orchestration: ownership checks, business
  validation, coordinating CRUD and services, assembling the response payload.
- **CRUD** (`core/cruds/`) — persistence only. Owns its own session via
  `core.database.database.session`; routes and controllers never take a `db` parameter.
- **Services** (`core/services/`) — external integrations, provider clients, reusable workflows,
  background work.
- **Schemas** (`core/apis/schemas/`) — wire contracts. **Models** (`core/models/`) — storage shape.

### Frontend layering

```
route/page → feature component → shared UI/hooks → API client → backend API
```

- Route files stay thin: layout, data boundaries, metadata, params.
- `src/features/<domain>/` owns workflow-specific UI and state.
- `src/components/` stays domain-neutral — no feature state imports.
- **All** backend calls go through `src/lib/api/`. No `fetch` in a component.

## Data model

Fourteen tables. The two that shape everything else:

- **`questions` / `question_versions`** — identity and taxonomy are editable; prompt, ideal
  answer, expected concepts, common mistakes and rubric live in an immutable version.
  `questions.source_key` is a stable, unique handle for authored content: primary keys are
  generated by the database, so without it re-running the content seed would duplicate the bank
  rather than update it. An attempt
  stores `question_version_id`, so a rubric edit can never change what a past grade meant.
  At most one version per question is `published`, enforced by a partial unique index.
- **`attempts`** — the unit of learning evidence. Every mastery score, review entry and
  recommendation derives from it. `session_questions` stores the server-decided composition so a
  refresh resumes the same session and a client cannot reshuffle to farm easy questions.

Supporting: `categories` (reference, seeded by migration), `users` / `profiles`, `sessions`,
`grade_events` (append-only grading audit), `skill_scores`, `subscriptions`, `entitlements`,
`billing_events` (append-only payment audit and webhook idempotency), `grade_flags`.

Email delivery has no table of its own: `sessions.results_email_sent_at` and
`profiles.last_nudge_email_at` record each send on the row the fact is about, and a sweep that
sets the marker only on success gives the same exactly-once guarantee a delivery log would,
without a second table to keep in step.

### Conventions

- Primary keys are `uuidv7()` — non-enumerable, and time-ordered so inserts append rather than
  fragment the index the way random v4 keys do. Requires PostgreSQL 18+.
- Timestamps are `timestamptz`, strings are `text`, money is `numeric`.
- Status columns are `text` with a CHECK constraint generated from a `StrEnum` via
  `core.constants.enums.in_check`, not a PostgreSQL `ENUM` type: adding a value is then a
  constraint change rather than an `ALTER TYPE` that cannot be rolled back cleanly.
- Foreign keys are indexed. `ON DELETE RESTRICT` protects grading provenance
  (`attempts.question_version_id`); `CASCADE` is used for genuinely owned data.

### Invariants the database enforces

Several product invariants are CHECK constraints, not just controller logic, because a violating
row corrupts the evidence permanently:

| Constraint | Guarantee |
|---|---|
| `ck_attempts_ungraded_has_no_score` | A grading failure never becomes a score of 0 |
| `ck_attempts_graded_has_result` | A graded attempt always carries score, band and timestamp |
| `uq_attempts_session_question` | A duplicate submit cannot create a second attempt |
| `ck_question_versions_published_is_complete` | No question enters the graded pool without a usable rubric |
| `uq_question_versions_one_published` | Exactly one rubric grades a question at any time |
| `ck_skill_scores_has_evidence` | Mastery is never shown without graded attempts behind it |
| `ck_profiles_consent_has_timestamp` | Recruiting consent is always auditable |
| `ck_users_has_auth_method` | An account can never lose every way to sign in |

`backend/tests/test_schema_invariants.py` asserts each of these against a real database.

## Authentication

Self-contained in the API — no external identity provider. Session state lives in cookies the
browser cannot read and in a revocable server-side token store.

```
POST /v1/auth/register    email + password, signs in immediately
POST /v1/auth/login       email + password
POST /v1/auth/google      verified Google ID token (needs GOOGLE_CLIENT_ID)
POST /v1/auth/refresh     rotates the refresh token
POST /v1/auth/logout      revokes the current rotation family
POST /v1/auth/logout-all  revokes every session for the user
GET  /v1/auth/me          the signed-in user
```

- **Passwords**: Argon2id via `argon2-cffi` defaults (64 MiB, t=3, p=4). A successful login
  transparently rehashes when the library's parameters harden.
- **Access token**: HS256 JWT, 15 minutes, in an `HttpOnly` `SameSite=Lax` cookie. It carries
  `sub`, `typ`, `iat`, `exp`, `jti` and **nothing else** — admin rights and account status are
  read from the database on every request, so suspending an account takes effect immediately
  rather than at the next expiry.
- **Refresh token**: opaque 384-bit random value, SHA-256 hashed in `refresh_tokens`, 30 days,
  rotated on every use. Not a JWT, because a session must be revocable.
- **Theft detection**: every rotation of one login shares a `family_id`. Presenting an
  already-rotated token means it was captured, so the **whole family** is revoked. Revoking only
  the replayed token would leave attacker and user alternating rotations indefinitely.
- **Rate limiting**: two buckets. Per-IP is deliberately loose (60/15 min) because students share
  campus NAT addresses and a tight per-IP limit would lock out a whole university; the tight
  limit is **per account** (8/15 min), which is what actually stops guessing and which IP
  rotation cannot evade.
- **Enumeration**: sign-in returns one message for both "no such account" and "wrong password",
  and hashes a dummy value when no account matches so timing does not distinguish them either.
  Registration's conflict message never confirms an address is registered.
- **Google**: the browser gets an ID token, the server verifies its signature against Google's
  JWKS and checks issuer and audience. Only `GOOGLE_CLIENT_ID` is stored, never a client secret.
  An unverified Google email is rejected — accepting one would let anyone claim an existing
  account by asserting its address.
- **Frontend**: `src/proxy.ts` silently rotates an expired access token and gates routes. Those
  redirects are **user experience only** — the API authenticates and authorises every request
  independently.

## Question bank

Content lives in `backend/seeds/questions.json` and is loaded by
`core.services.questions.seed_service`. Forty questions are shipped, five in each of the eight
categories, at difficulty 1-4. The schema allows difficulty 5; no question is authored at that
level yet, so a selection rule that requires one will find nothing.

```
GET    /v1/categories                                    public taxonomy
GET    /v1/sessions/{id}/questions/{qid}                 a question from your own session

GET    /v1/admin/questions                               filtered, keyset-paginated list
GET    /v1/admin/questions/coverage                      per-category readiness
POST   /v1/admin/questions                               create, with an optional first version
GET    /v1/admin/questions/{id}                          question with version history
PATCH  /v1/admin/questions/{id}                          taxonomy only
PUT    /v1/admin/questions/{id}/status                   activate / retire
POST   /v1/admin/questions/{id}/versions                 new version, optionally published
GET    /v1/admin/questions/{id}/versions/{vid}           full grading content
PATCH  /v1/admin/questions/{id}/versions/{vid}           edit a draft, in place
POST   /v1/admin/questions/{id}/versions/{vid}/publish   publish, superseding the previous
GET    /v1/admin/questions/{id}/versions/{vid}/validation rubric completeness, without publishing
```

- **Every admin route returns 404, not 403, to a signed-in non-admin.** The dependency is declared
  on the router rather than per route, so an endpoint added later cannot be left unprotected by
  omission. The web pages mirror this: their `generateMetadata` runs the same gate, because a
  static `metadata` export is streamed even when the component then calls `notFound()` — which
  would confirm the route exists and name it.
- **Drafts are editable in place; published and superseded versions are frozen.** The
  immutability that matters is of versions that have graded something, and a draft never can:
  sessions are composed only from published versions. Freezing drafts too would burn a version
  number on every typo and bury real rubric history in editing noise.
- **Rubric completeness is validated before publication**, by
  `core.services.questions.rubric_service`. Blocking errors are separated from quality warnings,
  so a marginal question can still ship when someone decides it should. The database CHECK is the
  floor; the validator is the standard.
- **Activation requires a published version.** An active question with no rubric would produce a
  grading failure for every student who drew it, surfacing far from its cause.
- **Seeding is idempotent by content hash.** A question is matched on `source_key`; a new version
  is published only when the authored content actually differs from what is published. Without
  that, every deploy would append an identical version and the history that explains past grades
  would become noise.

## AI grading

```
route → controller → attempt persisted → background task
                                             ↓
                       GradingService → GradingProvider → GroqProvider
                                             ↓
                        validate → persist result + grade_event
```

`core/services/ai/` is the only place that knows a model is involved. Everything above it
consumes `GradeResult`.

| Module | Responsibility |
|---|---|
| `types.py` | `GradeContext`, `GradeResult`, failure kinds. The domain boundary. |
| `prompts.py` | Prompt text, output contract, injection defences, `PROMPT_VERSION` |
| `provider.py` | The `GradingProvider` interface and the configured-provider factory |
| `groq_provider.py` | Every Groq-specific detail, and nothing else |
| `openrouter_provider.py` | The same for OpenRouter, kept as an alternative |
| `fake_provider.py` | Deterministic local grading; the default, so a fresh clone works |
| `grading_service.py` | Orchestration, validation, retries, audit |
| `benchmark.py` | Runs labelled answers through the real path and scores the grader |

- **Submission returns before grading runs.** The attempt is persisted, a background task grades
  it, and the client polls `GET /v1/attempts/{id}`. Grading inline would hold the request open for
  the length of a model call and put the answer at the mercy of an HTTP timeout.
- **A grading failure never becomes a score of zero.** A failed attempt keeps its answer, carries
  no score, and goes back to `pending` for the sweep or to `failed` once retries are exhausted.
  The `ck_attempts_ungraded_has_no_score` constraint enforces this in the database too.
- **Two retry mechanisms, deliberately.** An immediate in-call retry (`GRADING_MAX_RETRIES`)
  covers a transient blip without making the student wait; the scheduled `grading_retry` sweep is
  the durability guarantee that survives a crash or a deploy. Only the sweep can lose nothing;
  only the immediate retry is fast.
- **The band is derived from the score**, using the question's own `band_thresholds`. The model is
  still asked for one and disagreement is recorded as a quality signal, but a score and a band
  that contradict each other cannot be resolved after the fact.
- **Concept keys are reconciled against the rubric and unknown ones are dropped**, never coerced
  to the nearest match. Keys feed mastery, so an invented key would fork a student's history and
  a wrong key would move a score that should not have moved.
- **Structured output is an aid, not the guarantee.** The provider constrains the response with a
  JSON schema where the model supports it, falls back to prompt-constrained JSON where it does
  not, and tolerates a markdown fence or surrounding commentary. Validation against the rubric is
  what makes a grade trustworthy, and it runs identically either way.
- **Prompt injection**: the student answer is fenced with a per-request random nonce, so a
  delimiter cannot be forged; the system prompt states that fenced content is graded, never
  obeyed; and the output schema is fixed, so nothing a student writes can add a field or invent a
  key. There is deliberately no keyword filtering — a student answering a question *about*
  injection is writing a correct answer, not attacking.

### Grading benchmark

```bash
uv run python -m scripts.run_grading_benchmark          # against GRADING_PROVIDER
uv run python -m scripts.run_grading_benchmark --json
```

Runs `backend/tests/fixtures/grading_benchmark.json` — human-labelled answers spanning excellent,
good, partial, weak, incorrect, plausible-but-wrong and differently-phrased-correct — through the
real grading path and reports agreement overall and per answer type. Run it before changing the
model, the prompt, or a rubric, and compare to the previous run. It is not a CI gate: real model
calls cost money and are not deterministic.

## Diagnostic

```
POST /v1/diagnostic                      start, or resume the one in progress
GET  /v1/diagnostic                      read the current diagnostic without creating one
GET  /v1/sessions/{id}                   session state and its ordered questions
POST /v1/sessions/{id}/attempts          submit one answer
POST /v1/sessions/{id}/complete          finish, once every question is answered
GET  /v1/sessions/{id}/results           results, or grading progress
```

Composition lives in `core/services/sessions/composition_service.py`; lifecycle and results in
`core/controllers/session_controller.py`.

- **24 questions, three per category, decided by the server.** The composition is written to
  `session_questions` at creation, so a refresh resumes the same questions and a client cannot
  reshuffle to farm easier ones.
- **Deterministic and per-student.** One student always composes the same diagnostic — a random
  draw nobody can reproduce is indefensible when a result is disputed — while a hash of the user
  and question IDs breaks ties, so students do not all get one shareable fixed set.
- **Difficulty ramps across the sitting, not within a category.** One easy question from every
  category, then one medium, then one hard. A student weak in Accounting learns that in the first
  eight minutes instead of after three Accounting questions in a row.
- **A thin bank fails loudly.** `CompositionError` with per-category shortfalls rather than a
  short diagnostic, which would silently misreport readiness for whichever category came up thin.
- **The diagnostic never shows a grade mid-sitting, and the API is what enforces it.** It is an
  assessment: a per-question score would let a student calibrate as they go and drain the results
  page of its payoff. Three endpoints hold the line, because three could reach the same scores —
  results answers 409, `GET /v1/attempts/{id}` returns state without the grade or reference
  answer, and `GET /v1/review` excludes attempts belonging to a diagnostic still in progress. The
  interface not asking is not the control; it was the only control until the Phase 12 security
  gate. Practice, where learning from each answer is the point, reveals grades immediately, and
  none of these three restrict it.
- **Completing does not wait for grading.** Grading is asynchronous; the results endpoint reports
  progress. Until every attempt resolves, results carry no scores at all — a readiness number
  computed from half the evidence is a wrong number, not an early one.
- **Results show stored mastery**, recomputed on first complete read, so the results page and the
  dashboard can never disagree about how ready a student is.

## Practice

```
POST /v1/practice        {"size": 5|10|20, "category_slug": null | "<slug>"}
```

Selection lives in `core/services/sessions/practice_service.py`. Sessions, answers and results
reuse the same endpoints as the diagnostic.

Priority is a weighted sum of four named signals, and the session stores the sentence explaining
which of them drove it:

| Signal | Weight | Meaning |
|---|---|---|
| Review due | 100 | Previously scored ≤ 65, and its spacing interval has elapsed |
| Weakness | 60 | Scales with the gap below full mastery in that category |
| Novelty | 25 | Never attempted |
| Difficulty fit | 15 | Closeness to the level implied by the student's mastery |

- **Spaced repetition is derived from attempt history**, not a separate queue: intervals of 2, 7
  and 21 days by attempt count. A question answered *well* is excluded for 21 days outright —
  re-testing something a student just demonstrated is the clearest way to waste a slot.
- **Explainability is a product requirement, not a style.** The interface tells a student
  *"Valuation is your weakest category, and 2 previous misses are due for review"*, and that claim
  is only honest if selection genuinely worked that way. The rationale is written at selection
  time and stored, because mastery moves and a sentence recomputed later would describe a state
  that no longer produced the set.
- **Two spread caps, both at 40% of the set.** One per category, so a single weak area cannot fill
  a set; one per difficulty, because difficulty fit is the only signal separating otherwise-equal
  candidates and without the cap a new student gets five questions at one level. The category cap
  is lifted when the student asks for a category; the difficulty cap never is.
- **Practice reveals the grade after every answer**, unlike the diagnostic. Learning from a single
  answer is the point here; deferring feedback would make it a second assessment.
- **Starting practice always creates a new set.** A student choosing "10 on Valuation" is asking
  for a new set, so any previous one is abandoned first.
- **Concept labels are returned only for the keys in that grade**, never the full declared list.
  Spaced repetition brings missed questions back, so handing over the whole checklist would let a
  student memorise it instead of learning.

## Review and progress

```
GET  /v1/review                    filtered history; category, score, missed concept, flagged, recent
POST /v1/attempts/{id}/flag        dispute one of your own grades
GET  /v1/progress                  per-category mastery, weekly trend, headline figures
```

`core/controllers/review_controller.py`. The attempt detail endpoint doubles as review detail.

- **The review list carries no answer text and no reference answer.** A list is scanned rather
  than read; the full evidence is on the detail endpoint, opened one at a time.
- **Review is history, so a diagnostic still in progress is not in it.** `list_for_user` takes
  `exclude_unfinished_diagnostic`, which review sets and the data export deliberately does not —
  an export must return everything the account holds, including answers to a sitting that is not
  over. Practice is never excluded; its grades are earned as they go.
- **An unmeasured category is `null`, never `0`.** "Not measured" and "measured badly" are
  different claims, and rendering the first as the second is a fabricated readiness signal. The
  interface renders it as "Not measured yet".
- **`movement` is `null` until there are two measured trend points.** A flat line and no data look
  identical on a chart, and only one of them means the student has not moved.
- **The mastery trend is reconstructed from attempts, not stored.** Mastery is already a pure
  function of (graded attempts, reference time), so each weekly point is recomputed from only the
  attempts graded by that date — no history table to keep in step, no backfill, and no way for a
  stored trend to disagree with the score it ends at. A point must never see evidence that did not
  exist yet, or the trend would show every student improving.
- **A flag is a statement, not a vote.** Flagging twice returns the existing flag; the unique
  constraint on (attempt, user) is the real guarantee.
- **A score without the answer it refers to is not reviewable**, so the graded attempt response
  includes the student's own answer.

## Billing and entitlements

```
GET  /v1/billing/plans          public catalogue; carries the caller's plan when signed in
GET  /v1/entitlements           the caller's access, capabilities and free-tier usage
POST /v1/billing/checkout       {"plan": "pro_monthly" | "season_pass"} → a hosted checkout URL
POST /v1/billing/portal         → a Stripe Customer Portal URL
POST /v1/webhooks/stripe        signature-verified provider events
```

`core/services/billing/` — `plans.py` is the catalogue, `provider.py` the boundary,
`stripe_provider.py` the only module that imports `stripe`, `entitlement_service.py` the access
decision, `webhook_service.py` the only writer of entitlements, `reconciliation_service.py` the
repair sweep.

- **A subscription and an entitlement are different records, deliberately.** The subscription
  mirrors what Stripe believes; the entitlement is what this application will honour. A cancelled
  subscription that is still paid through the end of the month is exactly that difference, and
  merging them would force a choice between billing honestly and giving the student what they
  paid for.
- **Free is the absence of an active grant**, never a stored `free` value. Every gated operation
  asks one question — does an unexpired grant exist — so a new plan name cannot quietly fall
  outside a value comparison.
- **Expiry is evaluated against the clock on every read.** A Season Pass carries its own end date,
  so it stops granting access the second it lapses. The reconciliation sweep marks it expired for
  readability; access never depended on that job having run.
- **Cancellation sets an end date rather than revoking.** `cancel_at_period_end` moves the grant's
  `active_until` to the paid-through date, and expiry then happens on its own with no further
  event required.
- **`past_due` does not revoke.** The card failed and Stripe is still retrying it; locking a
  student out mid-preparation over a decline that resolves itself in a day is a worse error than
  a day of unpaid access. Access ends when the subscription actually terminates.
- **Webhooks are idempotent by database constraint.** The event is inserted into `billing_events`
  *before* it is acted on, and the insert decides whether this delivery processes it. A
  check-then-write would let two simultaneous deliveries both pass the check. Most handlers are
  naturally idempotent anyway — but a Season Pass is a one-time payment with no subscription to
  key on, so a replayed `checkout.session.completed` would hand out a second pass.
- **Ordering is decided by the provider's clock, not ours.** Stripe does not promise ordering, so
  `subscriptions.last_event_at` records the `created` timestamp of the last event applied, and an
  older event is skipped. Without it a redelivered `updated` from before a cancellation would
  restore paid access.
- **A full refund revokes; a partial one does not.** A partial refund is a support gesture, and
  taking back the whole recruiting season over it turns a resolved complaint into a new one.
- **Reconciliation repairs, but never grants.** The hourly sweep asks Stripe what is true and
  fixes the mirror, revoking access the provider says has ended. It does not create grants — an
  active subscription with no grant means an event was lost, and that is logged for a human
  rather than silently papered over.
- **There is no fake payment provider.** A fake grader produces an obviously local score; a fake
  payment provider would produce paid access indistinguishable from bought access. Local
  development uses Stripe test mode and `stripe listen`.

### Free tier

`FREE_PRACTICE_SESSIONS` sets, `FREE_DAILY_GRADED_ATTEMPTS` graded answers in a rolling 24 hours,
and one diagnostic. Every limit is enforced in the API and mirrored — never decided — by the
interface.

- **The diagnostic is never capped by the grading limit.** A 24-question sitting would exhaust any
  sane daily cap on its own, and a half-graded diagnostic measures nothing. It is bounded by the
  one-diagnostic rule instead.
- **The grading check runs after the duplicate check and before the insert, and the check and the
  insert are held together under a per-user lock.** A client retry of an answer that is already
  stored is never refused, and a refusal never leaves a stored attempt that will never be graded.
  The lock (`commons/locks.py`) is what makes the limit real: apart, the check and the write are a
  check-then-act, and twenty simultaneous submissions were all accepted against a limit of fifteen
  — every one a paid model call. It is per user, so students never contend, and it fails open on a
  Redis outage, like the rate limiter: losing the counter store must degrade a spending control,
  never stop a student answering.
- **The allowance is counted from submission, not from completed grading.** Grading is
  asynchronous, so counting finished grades leaves the whole submit-to-grade window uncounted, and
  answers submitted faster than they grade are invisible to the cap. The spend is committed when
  the answer is accepted.
- **The daily grading counter excludes diagnostic answers.** The diagnostic is exempt from the cap,
  not merely permitted to exceed it — counting its 24 answers filled a 15-answer allowance and
  refused every practice answer for a day to a student who had practised nothing. The counter has
  to agree with the exemption; the diagnostic is bounded by the one-diagnostic rule instead.
- **An abandoned practice set does not spend an allowance.** Starting a set abandons the previous
  one, so counting abandoned sets would charge a student two of three for changing their mind
  about set size.
- **The rolling window is 24 hours, not a calendar day.** A calendar reset hands two allowances to
  anyone willing to wait for midnight, and gives students in different timezones different
  products.
- **A refusal is a 402 carrying its reason and numbers**, so the interface can say "you have used
  3 of 3 practice sets" rather than "upgrade required". A student stopped mid-task is owed the
  reason before the offer.

## Email and analytics

```
GET  /v1/account/email-preferences    the caller's own preferences
PUT  /v1/account/email-preferences    update them, signed in
POST /v1/emails/unsubscribe           one-click, token-signed, no session
POST /v1/analytics/events             the two events only a browser can observe
```

`core/services/email/` — `templates.py` renders, `provider.py` is the boundary,
`resend_provider.py` sends, `log_provider.py` is the default, `unsubscribe.py` mints and verifies
tokens, `email_service.py` orchestrates. `core/services/analytics/` — `events.py` is the
vocabulary, `service.py` sanitises and dispatches, `retention_service.py` detects return windows.

### Email

Three messages: diagnostic results and payment receipt (transactional), and the weekly weak-area
nudge (lifecycle).

- **The send marker is written after the provider accepts, never before.** `sessions.results_email_sent_at`
  and `profiles.last_nudge_email_at` are the exactly-once guarantee: a failure leaves the marker
  unset so the next sweep retries, and a success is never repeated. Marking first would turn one
  provider outage into results emails that are never sent.
- **Results are mailed by a sweep, not on completion.** Grading is asynchronous, so at the moment
  a student submits their last answer none of it may be graded. The sweep selects only diagnostics
  where every attempt has resolved — a score computed from half the answers is a wrong number, not
  an early one.
- **A wholly ungradeable diagnostic is still mailed**, saying so. There is nothing left to wait
  for, and silence would leave the student expecting an email that will never arrive.
- **Study reminders default ON; marketing defaults off.** A reminder is the product working — a
  spaced-repetition tool that never says something is due has stopped being one — and every one
  carries a one-click unsubscribe, which is what makes the default defensible.
- **Unsubscribe needs no session.** A signed HMAC token names the recipient; nothing is stored, so
  a link in a six-month-old email still works. Requiring a sign-in to stop mail is how a product
  gets reported as spam instead of unsubscribed from.
- **An emailed link can only ever turn mail off.** The endpoint writes `False` rather than taking a
  value from the caller, so a token cannot be replayed to re-subscribe. Re-subscribing needs a
  sign-in — the correct asymmetry.
- **The unsubscribe page acts on a click, not on load.** Mail scanners and link previewers fetch
  every URL in a message; a GET-triggered unsubscribe would unsubscribe people who never opened
  the email.
- **A nudge with nothing to say is skipped, and the skip is not marked.** Marking it would push
  that student a further week back every week, forever.
- **No message carries rubric content.** Scores, category names and counts only. Email is
  forwarded, archived and indexed by systems this application does not control.
- **The receipt confirms access, not the charge.** Stripe issues the tax receipt and holds the
  amounts; a figure rendered here would have to be kept in step with the provider's own record,
  and a wrong number on a receipt is worse than no receipt.

### Analytics

- **Two allowlists, and they are the point.** `AnalyticsEvent` fixes event names so a funnel does
  not break the day someone writes `diagnostic_complete`. `SAFE_PROPERTY_KEYS` fixes what may
  travel with them — an allowlist, because a blocklist has to anticipate every name someone might
  give an answer field and only has to be wrong once.
- **Raw student content never reaches analytics.** Undeclared keys, non-scalars and strings over
  `MAX_PROPERTY_LENGTH` are dropped in `sanitise`, once, rather than at twenty call sites. The
  length rule is the backstop: an answer is never 120 characters.
- **A browser may assert two events.** `landing_view` and `paywall_reached` genuinely only happen
  in a browser; everything else is recorded server-side, where the event is a consequence of work
  the API did. An event a client can assert is an event a client can fabricate, and
  `checkout_completed` from an anonymous POST would corrupt the number the product is measured on.
- **Analytics can never fail a request.** `track` dispatches onto the loop and returns; every
  provider swallows its own failures. Jobs use `record`, which awaits.
- **`checkout_completed` is recorded in the webhook**, next to the entitlement write, for the same
  reason the entitlement is written there: the browser returning from checkout knows the payment
  succeeded, and that is not evidence.
- **Retention is detected by a sweep, deduped in Redis.** A return window is entered, and no single
  request knows it is the first of one. A lost dedupe key costs one duplicated point on a chart,
  which is exactly what Redis is for here.

## Coding standards

### Backend

- **Every** new or modified function and method needs a docstring: a purpose line, then a line on
  behaviour or the business rule. Add `Args`, `Returns`, `Raises` when they apply.
- Logging via `from core import logger` / `logging = logger(__name__)`:
  - route entry — `logging.info("Calling POST /v1/attempts endpoint")`
  - controller/service/CRUD entry — `logging.info("Executing ClassName.method_name")`
  - expected business rejection — `logging.warning(...)`
  - failure — `logging.error(f"Error in ClassName.method_name: {error}")`
- Wrap route handlers in `try`/`except`: re-raise `HTTPException` unchanged, convert unknown
  exceptions to a generic 500. **Never** collapse a meaningful 400/401/403/404/409 into a 500.
- Never log secrets, tokens, API keys, passwords, prompts, or rubric content.

### Frontend

- Server Components by default. `'use client'` only where interaction genuinely requires it.
- Every user-facing workflow needs loading, empty, error, disabled, success, and permission states.
- Never render a raw exception message. `ApiError` from the client layer is already normalised.
- Style with design tokens from `src/styles/globals.css`, not one-off values.
- **Mono is the grader's voice; sans is the student's.** Scores, bands, concept keys,
  category labels and difficulty are set in `--font-mono`; prose a person wrote or reads is
  set in `--font-sans`. Applied without exception, it is what makes machine judgement legible
  at a glance and is the product's strongest typographic signal.
- **Colour is scarce.** The band colours carry a grade and appear nowhere else; the accent is
  for focus, links and active navigation. Nothing on any surface is coloured decoratively.
- **The runners render without the shell but keep `SessionExit`.** "No distractions" and
  "no way out" are different things.

## Invariants

These are product-critical. Breaking one is a defect, not a style issue.

1. **The server is authoritative.** Entitlement, score, question selection, diagnostic
   composition, mastery, and free-tier limits are decided server-side. The client may hide a
   control for UX; the API still enforces it.
2. **Rubrics never leave the server before submission.** Ideal answers, expected concepts and
   common mistakes must not appear in any pre-submission response. Enforced by response schema
   shape, not by client behaviour.
3. **An answer is never lost to an AI failure.** Persist the attempt first, then grade. A grading
   failure marks the attempt pending or failed — never score 0.
4. **Grading history is immutable.** An attempt points at the `question_version` used when it was
   graded. Editing a rubric creates a new version; it never rewrites past grades.
5. **Entitlements are written only from verified payment events.** Not by the checkout
   endpoint, not by the success page, not by a support script. Webhook signature verified
   first, then the event is inserted into `billing_events` — the unique constraint on
   (provider, event ID) is what makes handling idempotent, not the handler's logic.
6. **Student text is untrusted.** It reaches the grading model as delimited data, never as
   instructions, and never influences the output schema.
7. **Recruiting consent defaults to false**, is independent of signup, and is revocable.
8. **No endpoint takes a user ID from the client.** Every account route operates on the
   authenticated caller, which removes the "change the ID in the URL" class of bug entirely.
9. **A question is reachable only through a session that belongs to the caller.** There is no
   endpoint that serves a question by ID, and owning a session does not grant access to questions
   outside its composition. Either would let one signed-in account walk the entire bank.
10. **A session serves the version it was composed with.** `session_questions` pins
   `question_version_id`, so publishing a new rubric cannot change the prompt an in-flight session
   is showing, or grade an attempt against a rubric the student never saw.
11. **Session composition is server-decided and stored, never re-derived on read.** A refresh
    resumes the same questions; a client cannot influence which questions it gets.
12. **Question selection is explainable.** Every session stores the reasons it was composed
    the way it was, and the interface only makes claims that selection actually acted on.
13. **Grading never runs before the answer is durable.** Persist, then grade. Every failure
    after that point costs a delay, never an answer.
14. **Provider details stay behind the abstraction.** Groq and OpenRouter specifics live only in the
   provider adapter; the rest of the application consumes `GradeResult`. Model names come from
   configuration, never from business logic.

## Common pitfalls

- **A new model needs importing in `backend/core/models/__init__.py`**, or Alembic autogenerate
  silently omits it from the migration.
- **Don't name a local variable `session`** in backend code or tests — it shadows the
  `core.database.database.session` context manager. Use `session_row` for a `Session` model.
- **`make test-api` derives the test database URL from `.env`** and uses `<POSTGRES_DB>_test`.
  Database and Redis tests skip cleanly when the stack is down; they do not fail.
- **`DATABASE_URL`/`REDIS_URL` use Compose service names**, not `localhost`. Use `localhost` only
  when running a process outside the containers.
- **Postgres 18+ mounts at `/var/lib/postgresql`**, not `/var/lib/postgresql/data`. The older path
  makes the container refuse to start.
- **`asyncio_default_test_loop_scope = "session"`** in `backend/pyproject.toml` is load-bearing.
  The Redis and database clients are process-wide singletons; a per-test loop closes underneath
  their pooled connections.
- **ESLint is pinned to the 9.x line.** `eslint-config-next` bundles an `eslint-plugin-react`
  that calls APIs removed in ESLint 10.
- **`eslint-config-next` 16 exports native flat config arrays** — spread them directly; do not
  bridge them through `FlatCompat`.
- **Docker group membership needs a fresh login shell.** A process started before
  `usermod -aG docker` keeps the old credentials and still gets `permission denied`.
- **Compose merges list fields.** `volumes: []` or `ports: []` in an override does **not** clear
  what the base file declared. Never put development-only mounts or published ports in
  `docker-compose.yml` expecting an override to strip them for production — they will ship.
- **Development containers run as `${HOST_UID}:${HOST_GID}`.** The image user is uid 1001; without
  this, anything the container writes into the bind mount (an autogenerated Alembic revision, for
  example) fails with `PermissionError`.
- **Containers log to stdout only.** `LOG_DIR` is opt-in and left unset in containers.
- **`python scripts/seed_questions.py` fails with `No module named 'core'`.** Running a script by
  path puts `scripts/` on `sys.path` instead of the application root. Use
  `python -m scripts.seed_questions`, which is what `make seed` does.
- **`conftest.py` clears `GOOGLE_CLIENT_ID` and the other integration credentials.** `make
  test-api` sources `.env` to find the database credentials, which exports everything else in it
  too — so a developer with Google sign-in configured locally would flip those endpoints from
  "not configured" to "configured" and fail the tests asserting the unconfigured behaviour.
- **The fake provider parses concept keys back out of the prompt.** Its line regex must not
  include `:` in the key character class — a greedy class matches through the separator, yields
  `net_debt:`, and every key is then dropped as undeclared. The symptom is a score of 100 with no
  concepts hit, in the default local configuration. Covered by
  `TestFakeProviderEndToEnd` in `tests/test_grading_service.py`.
- **A test module that exercises grading failures should zero `RETRY_BACKOFF_SECONDS`** in an
  autouse fixture. Three tests slept three seconds each through the real backoff before this.
- **The backend suite is dominated by `QuestionSeeder().run()`**, which ~40 tests call to get a
  full bank; each run is roughly 240 small transactions. That is most of the suite's ~2.5 minutes.
- **`useRef(Date.now())` fails the `react-hooks/purity` lint rule.** Reading the clock during
  render is impure; set the ref in an effect instead.
- **Fake timers and `waitFor` fight each other.** A component that polls on an interval is
  simplest to test with real timers and a generous `waitFor` timeout; `vi.useFakeTimers` plus
  `waitFor` stalled the practice runner's grade reveal until it was removed.
- **`CategoryBreakdown` renders on both the diagnostic results and the practice summary**, so its
  copy must not name either one.
- **An empty `missed_concepts` list is not evidence of full coverage.** A grading failure, or a
  response whose keys were all rejected, produces the same empty list, so the interface only
  claims full coverage where the score supports it.
- **A Client Component that seeds form state from props needs a `key`.** `useState` initialisers
  do not re-run on a client-side navigation that only changes props, so the admin version editor
  showed the previous version's content until it was keyed on the version ID. This is covered by
  `web/tests/VersionEditor.test.tsx`.
- **Literal routes must be declared before their `{param}` siblings.**
  `/v1/admin/questions/coverage` sits above `/v1/admin/questions/{question_id}`, or `coverage`
  parses as a question ID and 422s.
- **Not every model supports `response_format`/`json_schema`.** Most of Groq's catalogue does
  not; only the GPT-OSS and Qwen models do. One that does not
  rejects the whole request with a 400; the provider detects this, remembers it per model for the
  process, and retries without the constraint. The output contract is therefore stated in the
  prompt as well as in the schema — dropping the schema must not drop the field names.
- **`MAX_OUTPUT_TOKENS` has to fit the longest legitimate grade.** A verbose model truncated
  mid-object at 900 and produced `finish_reason=length` with unparseable content; a truncated
  grade is a wasted paid call, not a saved one.
- **A test that exercises a grading failure must patch `RETRY_BACKOFF_SECONDS` to 0**, or it
  really sleeps through the retry budget. One benchmark test took 55 seconds before this.
- **Rate-limit counters are cleared between tests** in `conftest.py`. Without it the suite
  exhausts the registration budget partway through and later tests fail with 429 for reasons
  unrelated to what they assert.
- **Authenticated pages need `export const dynamic = 'force-dynamic'`.** The cookie read happens
  behind a dynamic `import('next/headers')`, which Next's static analysis does not see, so the
  build otherwise tries to prerender them and fails with an unreachable API.
- **Next 16 renamed `middleware.ts` to `proxy.ts`** (exporting `proxy`). Use the new convention.
- **`typedRoutes` rejects runtime-built route strings**; cast them with `as Route` from `next`.
- **The app sends `X-Frame-Options: DENY`** (set in `infra/Caddyfile`), so it cannot be
  iframed — including for responsive testing. Reproduce a narrow viewport by stripping the
  `sm:`/`md:`/`lg:` class variants instead; those classes are the only difference between the
  mobile and desktop renders. Expect a hydration warning afterwards: removing classes React
  expects is the tool, not the product.
- **Route-level `not-found.tsx`, `error.tsx` and `loading.tsx` are load-bearing.** Without
  them Next renders its own: an unstyled 404 with nothing to click, and an
  "Application error: a server-side exception has occurred" screen that violates the rule
  against showing a raw exception. `error.tsx` must never render `error.message` — show
  `error.digest`, which Next also writes to the server log.
- **A usage counter can exceed its allowance.** A limit lowered by configuration, or answers
  graded under a larger one, both produce it. Clamp before rendering `used of limit`, or the
  interface reports "53 of 15 used".
- **A Stripe object is not a dict.** `stripe.Webhook.construct_event` returns an `Event`, which
  has no `.get` and raises on a missing key. Convert once at the provider boundary with
  `.to_dict()` (which recurses by default) and treat the result as ordinary untrusted data.
- **The webhook route must read `await request.body()`, not a parsed model.** The signature covers
  the exact bytes Stripe sent; letting FastAPI parse and re-serialise the payload changes them and
  fails every verification.
- **Webhook status codes are instructions to Stripe.** A bad signature is 400, which stops it
  retrying a payload that will never verify. A handler failure must be a 5xx so it *does* retry —
  answering 200 to a delivery that changed nothing discards a payment silently.
- **`conftest.py` clears `STRIPE_SECRET_KEY` alongside the other integration credentials**, so
  billing tests opt in through the `stripe_configured` fixture. That keeps the unconfigured
  behaviour — what a fresh clone gets — testable rather than assumed.
- **An analytics property that is not in `SAFE_PROPERTY_KEYS` is silently dropped.** That is
  the point, but it means adding a property to an event needs a line in `events.py` too, or
  the event arrives without it and nothing complains.
- **`track` does nothing outside a running event loop.** It dispatches onto the loop, so a
  synchronous script or an import-time call records nothing. Scheduled jobs use `record`.
- **Unsubscribe tokens are signed with `JWT_SECRET`.** A token minted by a process with a
  different secret — a local script against a containerised API, for example — verifies as
  invalid, and the endpoint answers 200 either way by design. Check the secret before
  concluding the endpoint is broken.
- **Rendering a set of questions uses `map_by_ids`, not `get_by_id` in a loop.**
  `CRUDQuestion.map_by_ids` and `CRUDQuestionVersion.map_by_ids` read a whole set in one round
  trip and return a mapping so the caller keeps its own ordering. Fetching per row made
  `GET /v1/sessions/{id}` cost 52 queries for a 24-question sitting and a page of review cost 43;
  both are now flat. Single-object endpoints keep `get_by_id` — they render one row.
- **A free-tier fixture must move `submitted_at`, not just `graded_at`.** The allowance counts
  from submission, so an attempt backdated only in its grade still lands inside the window and the
  rolling-window test fails for a reason that has nothing to do with the rolling window.
- **A limit that is a check followed by a write is not a limit.** Both free-tier gates were
  check-then-act; concurrent requests all read the same pre-write count and all passed. The
  grading gate is now serialised per user. The practice-set gate is a different shape — it is
  checked when a set is *started* but counted when a set is *answered*, so starting many sets
  before answering any still exceeds it. That one is a semantic gap, not a race, and a lock does
  not fix it; see `docs/security-review.md` finding 5.
- **A product rule that spans endpoints has to be enforced at every one of them.** "The
  diagnostic shows no grade mid-sitting" was true of the results endpoint and of the interface,
  and false of `GET /v1/attempts/{id}` and `GET /v1/review`, which reached the same scores by
  another route. When adding a surface that reads attempts, check it against
  `docs/security-review.md` finding 1 — and note that the diagnostic response hands the client an
  `attempt_id` per question, so no ID has to be guessed.
- **A deployed environment refuses to boot on a `.env.example` placeholder.** `JWT_SECRET` and
  `DATABASE_URL` are checked for the published marker strings when `ENVIRONMENT` is `production`
  or `staging`. If a deploy fails at startup complaining about a placeholder, generate a real
  value (`openssl rand -base64 48`) — do not lengthen the placeholder to satisfy `min_length`.
- **A completed or abandoned session needs `finished_at`.** `ck_sessions_finished_at_matches_status`
  rejects the row otherwise, which is easy to trip when building fixtures directly.

## Definition of done

A feature is done when data flows end to end, error and permission states work, persistence
works, tests exist and pass, the UX is complete, documentation matches reality, and security
concerns are addressed. Not when the page renders or the API returns 200.

Do not document behaviour that does not exist. Verify claims against the code or a command's
actual output.
